One card, one question, one breath.

The accented line under each question is the whole answer. Say it and stop. Everything below it is only for a second follow-up, and a card you cannot find in three seconds is worthless — use the bar above.

Rule for every card: claim exactly what was built, and name the limit before the questioner does. In a pitch about grounding, an overclaim is self-refuting.

1
LLM code

"You're running LLM-generated code?"

Yes — in a subprocess with a kill-timer, never in the process that holds the report. Loading a probe executes it, so loading happens inside the sandbox too, not in the parent. Firecracker is the year-two answer for probes running against customer infrastructure.

If pressed: probe code is the only code Keel executes that Keel did not ship, and it is the reason the architecture has a parent and a child at all. A synchronous while(true) cannot be preempted inside a JS process, so an in-process time guard is fiction — the only real timeout holds a process handle. Probes are also small, reviewable code by design, which is the point: a human can reject one.

Enforced today — say these four, they were exercised

Loading counts as running. All probe code — including the import, which executes module top-level — runs only in a kill-timed child process. The parent that holds the report imports nothing a probe wrote.

A hostile probe costs ten seconds and nothing else. A synchronous while(true) is killed by the parent at ~10.0 s; every node then falls through to agent judgment and the run exits 0. It cannot hang the run and it cannot classify anything.

A probe that throws is skipped and named in the output — not silently ignored, and it does not decide.

A probe that returns unknown is rejected at assess-time, inside the child. The type excludes it and the runtime rejects it anyway, because unknown is a claim about the world and only the agent makes one. That is what keeps the class unshoppable: a lazy probe degrades to ask, never to looks fine.

The network line — closed, and it is platform-conditional On macOS: the process re-executes itself under sandbox-exec with a deny-default profile before it touches a probe. That profile blocks network of any kind and filesystem writes anywhere, allows no exec but bun, denies the credential paths (~/.ssh, ~/.aws, ~/.gnupg, ~/.config/gh, ~/.netrc), and forwards no API keys. Everywhere else it is not enforced, and the tool says so itself — this is the sentence it prints, so say this and not a paraphrase: "sandbox NOT enforced: probe code ran in a child process with a stripped environment — no inherited credentials — under the parent's kill-timer, but network access and filesystem writes were NOT confined." It goes to stderr and into warnings, never silently. Not claimed, and say so before they ask: read confinement (a probe can read what you can read, minus those credential paths), exfiltration through the verdict text a probe returns, and any CPU or memory bound. A hang is the parent's problem by design. An adversarial review found a hole here and it is closed. A probe could force its own unconfined re-run by exiting 0 with no output — empty stdout is under the probe's control. Degradation now requires a non-zero exit and sandbox-exec's own stderr diagnostic, which the confined code cannot forge. A confined child that exits quietly is treated as a probe defect: every node pends, and nothing re-runs unconfined.
Do not say "It's sandboxed" as a whole-cloth claim. Name the mechanism: subprocess, parent kill-timer, stripped environment. If the deny-default sandbox-exec profile is not in force on the machine you are demoing — non-macOS, or KEEL_SANDBOX=0 — the correct sentence is: "subprocess, stripped environment, killed on a timer; network isolation is platform-conditional and I am not going to claim it here."
2
subjective

"Isn't the classifier subjective?"

Every verdict ships a falsifiable causal-path argument — what produces this signal, and can the actor write to it. The argument is the evidence, and you can check it in seconds without trusting the model.

If pressed: the second half of the answer is the repeatability number — verdict agreement across independent runs on the same target. Stability here is a property of the loop, not of the agent: constrain the environment and outcome variance collapses even while action-level variance stays high. That is a formal result, not a hope.

And the failure mode is named in the schema. A verdict whose argument restates its class — "self-referential because it is self-referential" — is a failed verdict, and the design system renders a visible defect banner when the argument is missing.

The strongest evidence — an argument that converged

Our own fixture contains zero unknown verdicts, and that is a result, not a gap — none was fabricated to fill a quota. The plan asked for at least two. The hard question was whether an unpinned out-of-repo dependency establishes a fork point outside the write boundary. Three independent judges were asked; all three landed it inside the boundary, because the resolution mechanism is itself committed — Makefile:16-22 selects from four actor-writable roots, so every copy it can resolve to is actor-writable. Strictly more informative than unknown.

That is the answer to "subjective". A subjective judgment does not converge across independent judges, and it does not come with a line number you can open. This one did both, and if the Makefile said something else the verdict would flip — which is what falsifiable means.

The pipeline: four classifiers over disjoint node groups, one adversarial reviewer per group (cross-assigned, none reviewed its own work), three-judge tie-break on the disputed question. The unknown render path is exercised synthetically instead, so nothing is untested.
Repeatability — there is no number, and the reason is the interesting part One target was re-run (tiktoken). Agent-only agreement is undefined: zero nodes were re-judged by an agent, because by that point the grown probe library decided every node. You cannot measure judgment stability on nodes no judgment touched. Do not say 100%. Pooled agreement on that re-run is 10 of 10, and it is not a stability claim — Keel's own summary says so in writing: probes are deterministic scripts that reproduce their own verdicts exactly, so counting them as independent re-judgment inflates the number toward 1.0 as the library grows, for reasons that have nothing to do with judgment. It is reported beside the agent number for audit, never as it. Say this: "We have not measured agent repeatability yet. The one re-run we have got swallowed by the probe library, which is a good problem and a real gap. What that re-run did do is turn into an audit — and it caught a bug in our own probe. Card 4."
Do not say "The model is very good at this." The claim is not model quality — it is that the argument is checkable by a human who distrusts the model.
3
well-tested

"Does a high ratio mean the repo is well tested?"

No. Shape, not quality — a repo can be 100% anchored with terrible tests. Anchoring says the signal comes from outside; it does not say the signal is sufficient.

If pressed: this is why the ratio never travels alone. The anchored count and the coverage print beside it on every surface, so a 1.0 over a single edge cannot masquerade as a result — and a bare ratio would reward deleting checks, which is the opposite of the point.

not_a_check is the one shoppable class: it sits outside the denominator, so misfiling a real check there inflates the score. It carries the same burden of argument as any other verdict, its count is printed beside the ratio, and the audit samples it like everything else.

Do not say "Passing", "failing", "good", or "healthy" about a ratio. Keel classifies; it does not grade. And unknown is not "pending" and not "needs review" — it is a traced failure to find the fork point, and it counts against the score.
4
who verifies

"The agent writes the probes — who verifies the verifier?"

Query provenance — the target cannot select the question, the output contract, or the audit sample. And we ran that audit on our own library once, by hand: it caught our own probe filing two real checks as not_a_check, the one class that inflates the score. We narrowed the probe.

If pressed: independence of the query is the binding invariant, not independence of the substrate. A verifier can share the actor's exact state and still be real, provided the actor could not have selected the question. That is why the audit has real query-independence even though it runs the same model.

What it cannot detect is shared-model bias — the audit and the original verdict come from the same class of system. That is disclosed rather than papered over, and it is mitigated two ways: probes are code that a human can read and reject, and every verdict carries an argument a human can check without running anything.

The structural guarantee is smaller and harder: a probe abstains by returning null and may never return unknown — that is a claim about the world, and only the agent makes it. So a lazy probe degrades to "ask", never to "looks fine".

The audit found real drift — this is the counter-metric working

Re-running tiktoken became an audit, because by then the library decided every node. Two disagreements, both toward the shoppable class. check-manifest and build sdist: the agent had judged them anchored; the probe filed them not_a_check.

The cause is legible in one sentence, which is the point of probes being code. The unfrozen-dependency-install probe matched pip install inside a multi-line run: block and condemned the whole step — but those steps also run check-manifest -v and python -m build --sdist.

Blast radius was checked, not assumed: 13 verdicts came from that probe, only these 2 were wrong, and both were confined to the audit side-file — no published report ever carried them. The match was narrowed; probe-versus-agent went 3/5 to 3/3.

"The counter-metric caught our own probe shopping the one class that inflates the score. That is the answer to who verifies the verifier: something did, it found a real defect in our work, and the two bad verdicts never reached a published number."

The limit, said before they ask One target, by hand, not on a schedule. The scheduled ε-audit was cut. There is no published agreement rate and no sampling fraction — do not say a percentage, do not say "we publish it", do not round one hand-run audit up to a corpus. The structural guarantee is what carries when the rate does not: a probe abstains by returning null and may never return unknown. A lazy probe degrades to ask, never to looks fine.
5
injection

"What if the repo prompt-injects your classifier?"

The target writes content. It never writes the query, the output contract, or the audit policy — those are frozen a level above it. Influence is bounded at L0; detection sits at L2, and the audit samples agent verdicts too, not only probe verdicts.

If pressed: prompt injection is conceded unsolvable at the reasoning level, industry-wide. Constraining the environment is the move that works, and it is the same move the whole architecture makes — which is why the answer to this question and the answer to "who verifies the verifier" are the same answer.

Adversarial-target hardening is year two, in the same lane as Firecracker. Say that plainly; a repo built to attack Keel specifically is not what tonight's number is measuring.

Do not say "We filter for injection." Nothing here filters prompts, and claiming a defense that does not exist is exactly the ungrounded assertion this product was built to find.
6
the oracle

"The same agent wrote the code and the tests — so what does a green test prove?"

That the execution is anchored and the oracle may not be. The runtime honestly decides pass or fail, but the assertions were authored inside the write boundary, so both can drift together and stay green. Keel classifies the execution axis and names that limit rather than silently upgrading it to proof.

If pressed: one case is rescued. An LLM judge scoring against a rubric frozen before generation is meaningfully stronger than an ad-hoc judge, because the verdict is a function of a constraint the generated content could not influence. Still not anchored — but the argument should record it, and it does.

This limit is deliberately in the product. Better named by us than found by a heckler at 2AM.

The proof that we apply this to ourselves

Keel measured this repository and found that at the measured revision our own bun test and tsc --noEmit were run by no workflow at all — so they gated nothing. Both had been classified anchored; the adversarial reviewer downgraded both to self_referential, because the rule is to classify the edge that actually blocks the merge, not the file that could have.

Say this one. It is the most credible thing the tool can say about itself: the first thing it did was cost us anchored edges on our own number, and it left us at 0.357 — the lowest ratio in our own corpus, against a pooled 0.853. A tool that only ever finds other people's problems is a marketing artifact.

If they ask whether we fixed it: yes — .github/workflows/test.yml exists now and is the fix. The published 0.357 is the number at the measured revision and has not been re-run. Shipping the finding against ourselves and then fixing it, in that order, is the only order that is not marketing.

7
high risk

"Your own installer just printed Snyk: High Risk."

It did, on every run — because the skill ships executable scripts, and those scanners score "contains code" on a package surface. Socket, on the same panel, found zero alerts. Everything that ships is plain TypeScript in the repo you just cloned; that is the point, and it is why the installer's own last line tells you to review it before you run it.

If pressed: an agent skill that shipped no code would have nothing to run. The heuristic is not wrong about what it measured — a skill-store package containing scripts — it is just not a finding about Keel. The details page is at skills.sh/broomva/keel if they want it after; do not open it on stage.

Keep the two code paths separate, because they get conflated and the answers are different. The code Keel ships is a fixed, reviewable set of files, pinned by version and diffable before it ever runs — that is what the scanner scored. The code Keel generates — the probes — is the card-1 answer: it runs only in a kill-timed subprocess with a stripped env and a read-only view of the target, loading included.

The move that would be self-refuting here is dismissing the score because it is inconvenient. Say what the scanner measured, say what it could not distinguish, and let the room check the files. That is the same standard Keel applies to a check.

Standing rule A number without its denominator is the move this product exists to expose. If you only have one of the pair, say the pair you have and name the missing half out loud.

Scope. Keel measures the shape of verification, not its quality. A repo can be 100% anchored with terrible tests. Anchoring says the signal comes from outside; it does not say the signal is sufficient.
